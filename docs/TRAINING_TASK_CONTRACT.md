# 训练任务接入约定

平台统一的是任务输入、执行、状态和产物的交接方式。模型结构、样本语义、损失、指标计算、ONNX 包装和后处理仍归算法代码所有。可以通过小型适配入口接入已有代码，无需把每个算法重写成同一个训练器。

## 当前可用的接入方式

| 环节 | 平台负责 | 算法或适配入口负责 |
| --- | --- | --- |
| 环境 | 登记镜像引用，运行容器 | 提供可用且验证过的镜像 |
| 数据 | 存档、生成版本、只读挂载 | 验证业务标签，明确 train/val/test 成员 |
| 代码 | 保存不可变代码版本，设置工作目录 | 提供入口及其参数 |
| 配置 | 拼接自定义命令参数，写入任务配置 | 解析参数，确定默认值和训练流程 |
| 计算 | 分配 GPU，限制 CPU/内存，启停及读取日志 | 使用分配的设备，不硬编码宿主机卡号 |
| 指标 | 解析约定的 results.csv | 写出每轮指标及所用数据范围 |
| 模型 | 收集、下载、注册产物 | 保存 checkpoint，正确构造并导出模型 |
| ONNX 验证 | 保存验证报告供查看 | 检查图、输入输出及数值一致性 |

## 文件与进程接口

- 数据根目录 `/workspace/dataset`：所选数据版本解压后的根目录，只读。
- 代码根目录 `/workspace/code`：所选代码版本解压后的根目录，只读；入口的相对路径取决于默认工作目录。
- 输出根目录 `/workspace/output`：可写，环境变量 `PLATFORM_OUTPUT_DIR` 指向这里。
- 平台任务 ID：`PLATFORM_RUN_ID`；任务配置文件 `/workspace/config/run.json`。
- 训练入口必须向 stdout/stderr 输出日志，正常完整完成退出 0；训练、导出或所要求的验证失败时退出非 0。
- 当前是一个容器里顺序执行全部阶段，平台未提供单独 prepare/train/export/validate 阶段的任务编排 API。

推荐的结果目录：

```text
/workspace/output/
  results.csv             # step,train/loss,val/loss；step 从 1 开始
  model.pth               # 或其他有意义的 checkpoint 文件名
  model.onnx              # 可选，由算法实际导出
  split_manifest.json     # 相对路径划分、哈希、随机种子
  run_summary.json        # 参数、环境、结果概况
  onnx_validation.json    # 可选，真实验证结果
```

这些 JSON 名称是建议约定，目前平台不自动解释它们的语义；可从产物下载阅读。`results.csv` 会被采集器解释，当前识别 loss、precision、recall、mAP 等已有列。不要伪造算法并未计算的指标。

当前自动收集 `.pt/.pth/.onnx/.csv/.json/.yaml/.yml/.png`，有文件数和总大小上限。成功任务才自动收集；整体失败时，已保存的文件仍可能在宿主机输出目录，但不保证出现在网页产物列表。

## 划分由谁做

优先将明确的划分成员或已划分的目录作为数据版本的一部分保存。具体采用随机、分层、按视频或按患者划分，由数据业务和算法决定，平台不应在不了解样本关系时强制随机拆分。

当前平台没有通用网页划分器。本次点位任务使用现有清单构造 `train/val`，原算法会直接读取这两个目录。算法仍支持内部划分，但本次不走这个分支。

## 导出由谁做

同一个 `.pth` 后缀可能保存裸 state_dict、带优化器的 checkpoint 或其他结构；模型类和前后处理也各不相同。平台不能只拿 `.pth` 就通用转换。

应由算法提供导出实现，平台以后可以用统一的配置和任务接口调用它。当前先在训练入口中顺序执行训练→原生导出→数值验证，产生真实 `.onnx`。平台现有模型注册表的 ONNX 导出接口仍是占位实现，不要用它替代算法的真实导出结果。

在将来多个算法都稳定遵守以上约定后，再增加结构化参数表单、阶段编排和标准 JSON 指标导入。这样是扩展公共接口，而非为每个算法增加一套平台分支。
